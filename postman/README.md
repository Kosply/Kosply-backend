# Kosply API catalog

The API surface, in two importable formats:

| File | What |
|---|---|
| `Kosply-API.postman_collection.json` | Postman collection, folders per domain, with example responses and test scripts |
| `Kosply-API.postman_environment.json` | Local environment (`baseUrl` → `http://localhost:3000`) |
| `collections/` | The same requests as one `.request.yaml` per endpoint |
| `specs/tables/` | Per-table notes for the Flutter client |

Both formats are generated by hand and are checked against the server by
`./scripts/postman/validate.sh`, which runs in CI.

## Setup

```bash
cp ../../.env.example ../../.env     # then fill it in
../../scripts/dev.sh setup           # install everything, migrate, seed
../../scripts/dev.sh start
```

Variables the catalog expects:

| Variable | Set by |
|---|---|
| `token` | `Auth/POST Login` (its test script captures it) |
| `userId` | `Auth/POST Login` |
| `internalApiKey` | **you** — must match the server's `INTERNAL_API_KEY` |
| `productId`, `conversationId`, `ticketId`, `reportId`, `modelId`, `verificationId`, `notificationId`, `adminUserId`, `resetCode` | captured by the test scripts as you go |

`internalApiKey` is the one you must set by hand. Everything under `Internal/`
is behind that guard, so without it those requests return 401 by design — the
test scripts assert it so the failure is obvious rather than mysterious.

## Run order

1. Boot and seed: `./scripts/dev.sh setup` then `./scripts/dev.sh start`
2. `Health/GET API Health` — confirm the server is up
3. `Auth/POST Register` (or `Login`) — captures `token` and `userId`
4. `Products/POST Create product` — captures `productId`
5. `Analytics/*` — needs a product; `PATCH Mark sold` first if you want `sales: 1`
6. `Verifications/POST Submit` then `Verifications/POST Review (admin)`
7. `Conversations/*`, `Support/*`, `Reports/*`, `Notifications/*`
8. `Admin/*` and `Models/*` need an ADMIN token; paste it into `token`
9. `AI/*` needs the agent running, else it answers 503 by design

## Notes per folder

- **Internal/** is the agent → server machine API. It uses `auth: noauth` and
  `x-internal-key`; the collection's bearer token is deliberately not applied,
  because these are machine calls and not user sessions.
- **AI/**, and `Conversations/GET Stream` + `GET Wait`, are SSE or long-poll.
  Postman buffers these rather than showing them live — use `curl -N` for the
  stream and `curl` for the polls. They are still listed so the shape is
  documented.
- **Analytics/POST Record event** is public and deduplicated per viewer inside a
  window: the first call returns `"recorded"`, repeats return `"deduped"`. That
  is correct behaviour, not a bug.
- Rate limits are real. `Auth` allows 10 login attempts per 15 minutes and
  `forgot-password` allows 5, so a full catalog run can legitimately produce a
  429 — log in once and reuse the captured `token`.

## Keeping it honest

```bash
./scripts/postman/validate.sh
```

It fails when a route exists in the server but not in either format, when a
collection entry points at a route that does not exist, when a `{{variable}}`
placeholder was left as a literal `:param`, or when an internal request is
missing `x-internal-key`. Run it after adding an endpoint — CI runs it too, so
a new route without a catalog entry fails the build.

## Mocks

Most requests carry a saved example response, so a Postman Mock Server can serve
the catalog with no backend running and Flutter can develop against it on day
one. Create the mock from this collection (Mock Servers → Create), then point
`baseUrl` at the mock URL.

The saved responses are snapshots, not generated output: if you change a
response shape in the server, update them here or the mock will teach Flutter
the old contract.
